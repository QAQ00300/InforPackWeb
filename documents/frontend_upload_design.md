# 文件上传页面设计文档（方案B）

## 1. 设计目标

支持多文件批量上传，每个文件对应一个独立的 SO 号（业务单号），实现高效的提单文件上传流程。

## 2. 核心逻辑

```
文件1 → SO NO: 123456 → hbl_no: 202607090001
文件2 → SO NO: 123457 → hbl_no: 202607090002
文件3 → SO NO: 123458 → hbl_no: 202607090003
```

**规则**：
- 每个文件必须对应一个 SO 号
- 同一个 SO 号可以重复上传（重新上传）
- SO 号相同但文件不同时，系统自动替换

## 4. 交互流程

### 4.1 上传文件

```
1. 用户拖拽或点击选择文件
2. 文件进入队列，显示在文件列表中
3. 每个文件自动生成一个 SO NO 输入框（空状态）
4. 用户为每个文件输入对应的 SO NO
5. 输入完成后，前端校验 SO NO 格式
6. 显示校验状态（✓ 正确 / ! 错误）
```

### 4.2 编辑文件

```
1. 用户点击某个文件的 [编辑] 按钮
2. 弹出文件详情弹窗或内联编辑
3. 用户修改 SO NO
4. 前端实时校验
5. 保存修改
```

### 4.3 删除文件

```
1. 用户点击某个文件的 [删除] 按钮
2. 弹出确认对话框
3. 用户确认后，文件从列表中移除
```

### 4.4 确认上传

```
1. 用户点击 [确认上传] 按钮
2. 前端校验所有文件：
   - 是否所有文件都已输入 SO NO
   - SO NO 格式是否正确
3. 如果校验失败，显示错误提示，不提交
4. 如果校验成功，调用后端接口：
   POST /api/v1/load/receive
   {
     files: [文件1, 文件2, 文件3],
     so_nos: ["123456", "123457", "123458"]
   }
5. 后端返回结果，前端显示成功/失败状态
6. 如果部分失败，标记失败的文件，用户可以修正后重新提交
```

### 4.5 重新上传

```
1. 用户输入已存在的 SO NO
2. 上传新文件
3. 后端查询该 SO NO 对应的记录
4. 如果记录存在且状态 ≤ 1（未确认），替换文件
5. 如果记录状态 ≥ 2（已确认），提示用户
6. 前端更新文件列表
```

## 5. 后端接口调整

### 5.1 文件上传接口

**请求：**
```
POST /api/v1/load/receive
Content-Type: multipart/form-data
```

**参数：**

| 参数名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| `files` | File[] | 是 | 上传的文件列表 |
| `so_nos` | string[] | 是 | SO号列表（与文件数量一致） |

**响应：**
```json
{
  "code": 0,
  "msg": "成功上传 2 个文件，失败 1 个",
  "data": {
    "total": 3,
    "success": 2,
    "files": [
      {
        "hbl_no": "202607090001",
        "so_no": "123456",
        "file_name": "提单文件001.xlsx",
        "file_size": 10240,
        "file_url": "http://192.168.0.94:8090/files/202607090001.xlsx",
        "status": "success"
      },
      {
        "hbl_no": "",
        "so_no": "123457",
        "file_name": "提单文件002.xlsx",
        "file_size": 8192,
        "file_url": "",
        "status": "failed",
        "error_msg": "SO号已存在且已确认"
      },
      {
        "hbl_no": "202607090003",
        "so_no": "123458",

  }
}
```

### 5.2 文件确认接口

**请求：**
```
POST /api/v1/load/confirm
Content-Type: application/x-www-form-urlencoded
```

**参数：**

| 参数名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| `hbl_no` | string | 否 | 单个提单号 |
| `so_no` | string | 否 | 单个SO号 |
| `hbl_nos` | string[] | 否 | 多个提单号（批量确认） |
| `so_nos` | string[] | 否 | 多个SO号（批量确认） |

**响应：**
```json
{
  "code": 0,
  "msg": "确认完成，成功 2 个，失败 1 个",
  "data": {
    "total": 3,
    "success": 2,
    "failed": 1,

        "hbl_no": "202607090002",
        "so_no": "123457",

  }
}
```

## 6. 状态展示设计

### 6.1 文件状态图标

| 状态 | 图标 | 颜色 | 说明 |
|------|------|------|------|
| 已上传 | ○ | 灰色 | 文件已上传，待确认 |
| 已确认 | ✓ | 蓝色 | 文件已确认，待发送 |
| 已发送 | → | 橙色 | 文件已发送到解析服务 |
| 解析成功 | ✔ | 绿色 | 解析完成，待审查 |
| 待审查 | 👁 | 紫色 | 已入库，等待人工审查 |
| 已转发 | ↗ | 蓝色 | 已转发到下游服务 |
| 已完成 | ✅ | 绿色 | 下游已接收 |
| 失败 | ✖ | 红色 | 出现错误，需要人工处理 |

### 6.2 状态流转提示

```
已上传 → [确认上传] → 已确认 → [自动发送] → 已发送 → [解析回调] → 解析成功
                                                                   ↓
                                                              待审查 ← 前端可操作
                                                                   ↓ [确认审查]
                                                              已转发 → [下游回调] → 已完成
                                                                   ↓
                                                              失败
```

## 7. 错误处理设计

### 7.1 前端校验错误

| 错误类型 | 提示方式 | 处理方式 |
|---------|---------|---------|
| SO NO 为空 | 输入框红色边框 + 下方红色文字 | 聚焦到该输入框 |
| SO NO 格式错误 | 输入框红色边框 + 下方红色文字 | 提示正确格式 |
| 文件数量超限 | 弹窗提示 | 限制继续添加 |
| 文件大小超限 | 弹窗提示 | 自动移除超大文件 |
| 文件格式不支持 | 弹窗提示 | 自动移除非支持格式的文件 |

### 7.2 后端返回错误

| 错误类型 | 提示方式 | 处理方式 |
|---------|---------|---------|
| SO NO 已存在且已确认 | 文件列表中显示红色错误提示 | 用户可以修改 SO NO 或放弃上传 |
| 文件上传失败 | 文件列表中显示红色错误提示 | 用户可以重新上传该文件 |
| 部分文件失败 | 顶部显示汇总提示 | 用户可以单独处理失败的文件 |

## 11. 关键设计决策

### 11.1 文件与 SO NO 的对应关系

**设计**：使用数组索引对应
```
files[0] → so_nos[0]
files[1] → so_nos[1]
files[2] → so_nos[2]
```

**优点**：简单直接，后端容易处理
**缺点**：前端需要确保数组顺序一致

### 11.2 重新上传的处理

**设计**：根据 SO NO 查询记录
```
1. 用户上传文件，输入 SO NO
2. 后端查询该 SO NO 是否存在
3. 如果存在且状态 ≤ 1，更新文件
4. 如果存在且状态 ≥ 2，返回错误
5. 如果不存在，创建新记录
```

**优点**：用户体验好，不需要知道 hbl_no
**缺点**：需要额外的数据库查询

### 11.3 错误文件的处理

**设计**：失败的文件保留在列表中，标记错误状态
```
1. 用户可以修改 SO NO 后重新上传
2. 用户可以删除失败的文件
3. 用户可以忽略错误，继续确认其他文件
```

**优点**：灵活，用户可以自主处理
**缺点**：界面需要处理多种状态

## 13. 总结

### 13.1 后端需要调整的接口

| 接口 | 调整内容 |
|------|---------|
| `/api/v1/load/receive` | 添加 `so_nos` 参数，支持多文件多SO号 |
| `/api/v1/load/confirm` | 支持按 `so_nos` 批量确认 |
| `/api/v1/resources/list` | 新增接口，支持按 SO NO 查询文件列表 |

### 13.2 前端需要实现的功能

| 功能 | 描述 |
|------|------|
| 文件上传 | 支持拖拽和点击上传 |
| SO NO 输入 | 每个文件对应一个输入框 |
| 文件列表 | 显示已上传文件及其状态 |
| 编辑/删除 | 支持单个文件的编辑和删除 |
| 批量确认 | 支持所有未确认文件的批量确认 |
| 错误处理 | 显示和处理上传错误 |
| 状态查询 | 查询文件处理状态 |

### 13.3 设计要点

1. **文件与 SO NO 的对应关系**：使用数组索引对应，简单直接
2. **重新上传逻辑**：根据 SO NO 查询记录，自动替换
3. **错误处理**：失败文件保留在列表中，用户可以单独处理
4. **用户体验**：实时校验、加载状态、操作反馈
